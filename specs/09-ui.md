## Purpose

The game can be played end to end over HTTP (Phase 8), but only with `curl`. This spec delivers the browser UI from design §10: a new-game page and a game table where the one human seat plays against 2–5 AIs. The UI holds the latest `PlayerUpdate`, offers only the server's legal moves, replays the returned events as an animation before showing the new view, shows the score sheet and the final ranking, resumes a game after a reload, and survives transport failures without applying a move twice. It never computes game rules or scores. It completes the first part of milestone M3: a full default-preset game playable in the browser on `pnpm dev`. It benefits the human player, and Phase 11, which deploys it.

## Scope

**In**
- Pages (client components, App Router):
  - `/` (`app/page.tsx`): new-game form and the "Continuar partida" link.
  - `/game/[id]` (`app/game/[id]/page.tsx`): the table, bidding, playing, event animation, score sheet, game-over screen.
- Pure client modules and components under `app/_client/` (Next ignores `_`-prefixed folders for routing): API calls, the stored-game slot, the update/version state, the event display model and queue, card display.
- Styling with CSS Modules plus one global stylesheet (`app/globals.css`). No CSS framework.
- All UI copy in Spanish; `<html lang="es">` stays.
- Tests in `tests/ui/` (pure logic and React component tests in jsdom), run by `pnpm test` and CI. `vitest.config.ts` changes so `pnpm test` also runs `tests/ui/**/*.test.{ts,tsx}` in a jsdom environment; the existing folders keep the node environment. This widens the `test` script scope defined in spec 00.
- New devDependencies, pinned exactly: `jsdom`, `@testing-library/react`, `@testing-library/dom`, `@testing-library/user-event`, plus `@vitejs/plugin-react` only if Vitest needs it to compile `.tsx`. Each chosen version's peer ranges must include the installed `react` 19.3, `vite` 8 and `vitest` 5, and `pnpm install` must report no peer-dependency warnings for them. No new runtime dependency.
- Docs: `docs/development.md` gains §17 "UI" (Known limitations becomes §18, cross-references updated); `docs/implementation.md` Phase 9 records decision 1 as taken (default preset only).

**Out**
- Choosing a rules preset in the UI (implementation §5 decision 1): the game always uses the server's default preset.
- Spectating, multi-human games, accounts, more than one remembered game per browser.
- A language switch or English copy.
- Card images or SVG assets.
- User-selectable animation speed.
- Playwright or any real-browser automated test. Layout and full play in a real browser are checked manually (VC-950–VC-954).
- Polling or push: AI moves arrive inside the human's own move response, so the UI never fetches on a timer.
- Any change to `src/**`, `app/api/**`, the HTTP contract, or the ESLint layer table.
- Browsers other than evergreen (BR-907).

## Functional Requirements

### New game (`/`)

- **FR-900 (Must)** — `/` shows a form with a name field (`Tu nombre`, text, `maxLength` 40) and an AI-count control offering exactly 2, 3, 4, 5 (`Rivales`), default 3. The submit button (`Empezar partida`) is disabled while the trimmed name is empty or a create request is in flight.
- **FR-901 (Must)** — On submit the UI calls `GET /api/presets`, takes `defaultPresetId` and that preset's `deck`, then calls `POST /api/games` with `{ humanName: <trimmed name>, aiCount, rulesPreset: defaultPresetId }`.
- **FR-902 (Must)** — On 201 the UI writes the stored-game slot `{ gameId, seatToken, deck, finished: false }` (FR-930), keeps the 201 `update`, tagged with its `gameId`, in a client-side module variable for the game page, and navigates client-side (`router.push`) to `/game/<gameId>`. The game page adopts that update and animates its `events` (game start, deal, AI opening bids) before enabling input, starting from the empty table of FR-920. The game page uses the kept update only when its `gameId` matches the route `id`, and clears it once adopted; on any other mount (no kept update, a different `gameId`, a hard navigation, a later visit) the page loads per FR-906.
- **FR-903 (Must)** — If either request in FR-901 fails (transport failure, any non-2xx), no slot is written, the user stays on `/`, the button is enabled again, and a message is shown: `No se pudo crear la partida. Probá de nuevo.` A 400 from create shows `Revisá los datos de la partida.` instead. No automatic retry on create.
- **FR-904 (Must)** — `/` shows a `Continuar partida` link to `/game/<gameId>` when a valid slot exists and its `finished` is `false`; otherwise it shows no link. The form is always shown; creating a new game replaces the slot.

### Loading the game page

- **FR-905 (Must)** — `/game/[id]` with no slot, or a slot whose `gameId` differs from `id`, shows `No tenés acceso a esta partida.` and a link `Nueva partida` to `/`, and makes no API call.
- **FR-906 (Must)** — `/game/[id]` with a matching slot and no kept update whose `gameId` matches `id` (FR-902) calls `GET /api/games/<id>` (no `since`) with `Authorization: Bearer <seatToken>`, adopts the update (FR-910) and shows its view. `events` is `[]`, so nothing is animated.
- **FR-907 (Must)** — If the load in FR-906 answers 401, 404 or 410, the UI clears the slot and shows, respectively, `Tu acceso a esta partida ya no es válido.`, `La partida ya no existe.`, `La partida no se puede continuar con esta versión del juego.`, each with a `Nueva partida` link.
- **FR-908 (Must)** — If the load in FR-906 fails in transport or with 5xx, the slot is kept and the UI shows `No se pudo cargar la partida.` with a `Reintentar` button that repeats the same GET.

### Update and version state

- **FR-910 (Must) — Version guard.** The UI keeps the latest adopted `PlayerUpdate`. A received update is adopted only if no update is adopted yet or its `version` is greater than the adopted one's; otherwise it is ignored (its events are not queued).
- **FR-911 (Must)** — Terms: the *adopted update* is the latest update accepted by FR-910; the *shown view* is what the table currently renders. Adopting a 201 or a 200 move response appends its `events` to the animation queue (FR-920). Adopting any other update (page load, 409, recovery GET) empties the queue and makes the shown view the adopted view at once, with no animation. Legal moves and the shown view come only from the adopted update or queued events, never from a client calculation.
- **FR-912 (Must)** — When the adopted view has `phase` `game-over`, the UI sets `finished: true` in the slot.

### Bidding and playing

- **FR-913 (Must)** — Bid buttons and clickable cards are shown only when the queue is empty (FR-937) and `legalMoves` is non-empty, and are enabled only when no move request is in flight or awaiting retry.
- **FR-914 (Must) — Bidding.** When the legal moves are bids, the UI shows one button per legal move, labelled with its `tricks`, in ascending order. A bid value that is not legal (e.g. the dealer's forbidden value) has no button.
- **FR-915 (Must) — Playing.** When the legal moves are plays, each card in `yourHand` whose card is the `card` of a legal move is shown enabled and clickable; every other card is shown dimmed and is not clickable. Cards keep the order of `yourHand`.
- **FR-916 (Must) — Action capture.** On a bid or card click, the UI captures `{ version: <adopted version>, moveId: <the legal move's id>, clientRequestId: <new id per FR-935> }` once, then sends `POST /api/games/<id>/moves` with that body and the seat token. Every retry of this action (FR-917) sends the identical body.
- **FR-917 (Must) — Transport retry.** A move attempt is a transport failure as defined in FR-936. After a transport failure the UI retries automatically after 1 s, 2 s and 4 s (3 retries). If all fail, it shows `No se pudo enviar la jugada.` and a `Reintentar` button; each click sends the same captured body once more, again with the 20 s timeout.
- **FR-918 (Must) — Move responses.**
  - 200 → adopt the body (FR-910).
  - 409 → adopt `update` from the body, then show `La partida avanzó; se actualizó la mesa.`
  - 403 or 422 → `GET /api/games/<id>?since=<adopted version>`, adopt the result (no animation, FR-911), and show `Esa jugada ya no es válida.` If that GET fails in transport or with ≥ 500, treat it like FR-908; if it answers 401/404/410, like FR-907.
  - 400 or 413 → same as 403/422 but with the message `Error inesperado.`
  - 401, 404, 410 → same as FR-907.
- **FR-919 (Must)** — Notices from FR-918 disappear after 4 s or when the next action starts.

### Event animation

- **FR-920 (Must) — Queue.** Queued events play one at a time, in order, on a *display model*. Each event's effect (FR-921) is applied when the event starts and then held for its delay; the next event starts when the delay ends. The display model starts from the view shown before the adoption; for the 201 update of FR-902 it starts from an empty table: the adopted view's seats with `cardCount` 0, `bid` null, `tricksWon` 0, no trump card, empty current and last trick, empty hand. When the queue empties, the shown view becomes the adopted view exactly.
- **FR-937 (Must) — State not changed by events.** While the queue is non-empty: no seat shows the turn marker (FR-924's highlight shows the acting seat instead); the score sheet, `phase` and the game-over screen come from the view shown before the adoption (the empty table of FR-920 has no score rows filled); no legal-move input is shown. All of them switch to the adopted view when the queue empties.
- **FR-921 (Must) — Event effects on the display model:**
  - `game-started`: no visible change, 0 ms.
  - `hand-dealt`: sets the trump card and `trumpCardInDealerHand`, the dealer and hand number; every seat gets `cardCount = cardsPerPlayer`, `bid = null`, `tricksWon = 0`; the current trick and last trick are emptied; the hand banner is cleared. The human's hand is set per FR-922. 600 ms.
  - `bid-made`: sets that seat's bid. 600 ms.
  - `card-played`: adds `{seat, card}` to the current trick, lowers that seat's `cardCount` by 1, and removes that card from the shown hand when the seat is the human's. 600 ms.
  - `trick-won`: marks the winner, increments its `tricksWon`, moves the current trick to the last trick and empties the current trick. 1200 ms.
  - `hand-completed`: shows a banner `Fin de la mano <handIndex + 1>` with each seat's bid and tricks from `result`. The banner stays until the next `hand-dealt` or the end of the queue. 1200 ms.
  - `game-over`: no visible change, 0 ms; the game-over screen appears when the queue empties (FR-926).
- **FR-922 (Must) — Hand after a deal.** At a `hand-dealt` event the shown hand becomes the adopted view's `yourHand`. (Only 201 and 200 move responses are animated, FR-911; in those, a `hand-dealt` is always for the adopted view's hand and the human plays no card after it.)
- **FR-923 (Must) — Skip.** While the queue is non-empty, a `Saltar` button is shown. Clicking it empties the queue and shows the adopted view at once.
- **FR-924 (Should)** — The seat that produced the event being shown is highlighted.

### Table, score sheet and game over

- **FR-925 (Must) — Table.** The table shows:
  - for every seat: name, `(vos)` on the human's seat, card count, bid (`—` when null), tricks won, a dealer marker on `dealer`, a turn marker on `toAct`;
  - the trump card, with `En mano del repartidor` when `trumpCardInDealerHand`;
  - the current trick with the seat of each card;
  - the last trick and its winner, when not null;
  - hand number and cards this hand: `Mano <handIndex + 1> de <handPlan.length> · <handPlan[handIndex]> cartas`;
  - the human's hand.
- **FR-926 (Must) — Game over.** When the shown view has `phase` `game-over`, the UI shows a ranking from `finalRanking`: place, name, total, in ascending place order. Tied seats show the same place. It shows a `Nueva partida` link to `/`. No bid or card input is shown.
- **FR-927 (Must) — Score sheet.** A `Planilla` button opens a panel over the table at every viewport width; `Cerrar` closes it. The panel has one row per entry of `handPlan`: hand number, cards, and per seat bid / tricks / points for hands in `scoreboard.hands`, empty for the rest. Each completed row also shows each seat's running total (the sum of that seat's `points` in that row and all earlier rows). A totals row shows `scoreboard.totals`.
- **FR-928 (Must)** — While `scoreboard.live` is present, the score sheet row of the current hand shows each seat's live bid, tricks and status: `on-track` → `En camino`, `made-so-far` → `Cumplida`, `busted` → `Pasada`.

### Stored-game slot

- **FR-930 (Must)** — The slot is one `localStorage` key, `la-podrida:game`, holding JSON `{ gameId: string, seatToken: string, deck: string, finished: boolean }`. Reading returns "no slot" when the key is missing, the JSON does not parse, or any field has the wrong type. Every read and write is wrapped in `try/catch`; a failure counts as "no slot" on read and is ignored on write.
- **FR-931 (Must)** — If the slot cannot be written in FR-902, the game is still playable in the current tab: the page uses an in-memory copy of the slot for the rest of the tab session. After a reload, FR-905 applies.
- **FR-938 (Must) — Slot ownership.** A game page changes the slot (FR-907 clear, FR-912 `finished: true`) only when the stored slot's `gameId` equals the page's route `id`, re-reading the slot just before the change; otherwise it leaves the slot untouched. Only FR-902 (a new game) replaces a slot belonging to another game.
- **FR-932 (Must)** — `localStorage` is read only after mount (in an effect), so server-rendered HTML and the first client render match and no hydration warning is logged.

### Cards

- **FR-933 (Must)** — A card is drawn as a CSS box with its rank and suit, from the slot's `deck`. A missing or unknown `deck` falls back to `french-52`.
  - `french-52`: suit `S` ♠ picas, `H` ♥ corazones, `D` ♦ diamantes, `C` ♣ tréboles; `H` and `D` in red. Ranks shown as their token (`A`, `K`, `Q`, `J`, `10`…`2`).
  - `spanish-40`: suit `O` oros, `C` copas, `E` espadas, `B` bastos, shown as the word, each in its own colour. Ranks `R` → `12`, `C` → `11`, `S` → `10`, others as their token.
- **FR-934 (Must)** — Each card has an accessible name: `<rank name> de <suit name>`, e.g. `10 de picas`, `Rey de copas`, `As de oros` (rank names: `A` As, `K` Rey, `Q` Reina, `J` Jota for french-52; `A` As, `R` Rey, `C` Caballo, `S` Sota for spanish-40; numbers as digits). A clickable card is a `<button>`.

### API calls

- **FR-935 (Must) — Request id source.** `clientRequestId` is `crypto.randomUUID()` when that function exists; otherwise a version-4 UUID string built from 16 bytes of `crypto.getRandomValues` (works outside secure contexts, e.g. `http://<LAN IP>:3000`).
- **FR-936 (Must) — Timeouts and transport failures.** Every API call in this spec (presets, create, load, recovery GET, move) is aborted when no response arrives within 20 s. A call's result is a *transport failure* when `fetch` rejects, the 20 s abort fires, the status is ≥ 500, a 2xx body is not JSON of the expected shape (a `PlayerUpdate` must have a number `version`, an array `events`, an object `view` with array `seats`, array `handPlan`, array `yourHand` and object `scoreboard`, and an array `legalMoves`; a 201 body must have string `gameId` and `seatToken` and an `update` of that shape; a presets body must have a string `defaultPresetId` and an array `presets` whose entries have string `id` and `deck`; deeper fields are trusted), a 409 body has no `update`, or the status is not one handled for that call by its FR (create: 201, 400 per FR-903; presets: 200; load and recovery GET: 200, 401, 404, 410 per FR-907/908; move: 200, 400, 401, 403, 404, 409, 410, 413, 422 per FR-918). Retrying a move after a transport failure is safe because the identical `clientRequestId` is deduplicated by the server (spec 07).

## Business Rules

- **BR-901 Server is the only rules authority.** The UI never decides legality, turn, trick winner, scores or ranking. It shows `legalMoves`, `toAct`, `trick-won.seat`, `scoreboard` and `finalRanking` as given. The only arithmetic it does is display bookkeeping from events (FR-921) and running totals of given points (FR-927). *Rationale:* design §10; one rules implementation. *Exception:* none.
- **BR-902 Layer boundary.** No file under `app/` outside `app/api/` imports a value from `src/**`, imports anything from `src/**` other than `src/domain` (types only), or imports anything from `app/api/**`. *Rationale:* Phase 0 layer rule; spec 08 known limit (`app/api/_lib/schemas.ts` pulls in server-only `src/state`). *Exception:* none. Lint enforces the `src` part; a static test enforces the `app/api` part.
- **BR-903 A move is applied at most once per action.** Every send of one user action carries the identical `{ version, moveId, clientRequestId }`; a new `clientRequestId` is generated only for a new click. *Rationale:* the server dedupes by `clientRequestId` (spec 07). *Exception:* none.
- **BR-904 Never go backwards.** The shown and adopted version never decreases (FR-910). *Rationale:* responses can arrive out of order after retries. *Exception:* none.
- **BR-905 The seat token stays in the browser.** The token is sent only in the `Authorization` header to `/api/games/<id>` routes, is never put in a URL, never logged with `console.*`, and never rendered. *Rationale:* architecture §8. *Exception:* none.
- **BR-906 No hidden information beyond the API.** The UI renders only what an adopted update or a queued event contains. *Rationale:* BR-801. *Exception:* none.
- **BR-907 Evergreen browsers.** Target: the latest two versions of Chrome, Edge, Firefox and Safari (macOS and iOS). No polyfills. *Rationale:* user decision. *Exception:* none.

## Non-Functional Requirements

- **NFR-901 Phone layout.** At a 375 × 667 CSS px viewport, `/` and `/game/[id]` have no horizontal page scroll, and every bid button and hand card is fully visible without horizontal scrolling (wrapping is allowed), in the two worst cases the default preset `argentina-fidepo` (deck `french-52`) can produce: (a) 5 AIs (6 seats) at an 8-card hand, bid buttons 0–8 (most seats); (b) 2 AIs (3 seats) at a 17-card hand, bid buttons 0–17, 29-row score sheet (most cards, buttons and rows). Each with the score sheet closed and open.
- **NFR-902 Tap targets.** Every bid button, clickable card, `Saltar`, `Reintentar`, `Planilla` and `Cerrar` is at least 44 × 44 CSS px.
- **NFR-903 Animation pacing.** Per-event delays exactly as in FR-921 (verified under fake timers); `Saltar` shows the adopted view within one rendered frame of the click.
- **NFR-904 Timeouts.** Every API call is aborted at 20 s (FR-936); move retry delays are 1 s, 2 s, 4 s (verified under fake timers).
- **NFR-905 Clean build.** `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build` pass, and the browser console shows no React error or hydration warning during the manual play-through.

## Data & Interfaces

### API usage (per spec 08; no changes)

| Call | When | Body / query | Handled statuses |
|---|---|---|---|
| `GET /api/presets` | New game | – | 200 → `{ defaultPresetId, presets[].deck }`; else FR-903 |
| `POST /api/games` | New game | `{ humanName, aiCount, rulesPreset }` | 201; 400 and else → FR-903 |
| `GET /api/games/{id}` | Page load | – | 200; 401/404/410 → FR-907; ≥ 500 / transport → FR-908 |
| `GET /api/games/{id}?since=v` | After 403/422/400/413 on a move | – | as page load |
| `POST /api/games/{id}/moves` | Bid / play | `{ version, moveId, clientRequestId }` | FR-918 |

All requests use `cache: 'no-store'` and the 20 s timeout and transport-failure rule of FR-936. Authenticated calls send `Authorization: Bearer <seatToken>`.

### Types

Imported with `import type` from `@/src/domain/types`: `PlayerUpdate`, `PlayerView`, `GameEvent`, `LegalMove`, `Card`, `ScoreBoard`. The presets and create responses and the error body are typed locally in `app/_client` (spec 08 shapes), because the UI may not import `app/api/_lib`.

### Client modules (`app/_client/`)

Pure modules have no React; `fetch`, `Storage`, the UUID source and timers are passed in, so `tests/ui` can test them directly:

```ts
// slot.ts — FR-930/931
export interface GameSlot { gameId: string; seatToken: string; deck: string; finished: boolean }
```

## Key decisions

- **Client components for both pages.** Everything they show depends on `localStorage` and on the seat token, which the server never sees outside an API call; server rendering would have nothing to render.
- **CSS Modules, no framework, no card images** (user choice): zero new runtime dependencies; cards are drawn with text and suit symbols.
- **Automated tests in jsdom only, no Playwright** (user choice): CI stays simple and fast. Trade-off: layout and tap-target NFRs (901, 902) and real-browser behaviour are checked only manually (VC-950–VC-954) and can regress unnoticed between phases.
- **In-process API in UI tests** (VC-945): the UI is exercised against the real handlers and `GameService` on `MemoryObjectStore`, so a contract mismatch with spec 08 fails a test rather than the manual run.
- **201 update handed over in memory** (FR-902): saves a GET and lets the opening AI bids animate; a hard navigation falls back to a plain load.
- **Only 201 and 200 move responses animate** (user choice): 409 and recovery updates can span several of the human's own actions, where the human's past hands are unknown to the client; jumping straight to the view avoids face-down placeholder rules.
- **Retry policy** (user choice): 20 s timeout, then 3 automatic retries at 1/2/4 s, then a manual button. Safe because the same `clientRequestId` is deduplicated by the server (spec 07).
- **Deck learned from `GET /api/presets`** (user choice): the view has no deck field and suit `C` is ambiguous between decks; sending `rulesPreset: defaultPresetId` explicitly keeps the stored deck consistent with the created game.

## Verification Criteria

Automated VCs run in `tests/ui/` under `pnpm test`. A full-game VC routes the UI's `fetch` to the Phase 8 handlers in process (`MemoryObjectStore`, real `GameService`), so the UI is tested against the real API contract.

### New game and slot

- **VC-900:** render `/`; empty name → submit disabled; name `"  "` → disabled; name `Ana` → enabled; AI control offers exactly 2, 3, 4, 5 with 3 selected. *(FR-900)*
- **VC-901:** submit `  Ana ` with 4 AIs against the in-process API → presets is called before create; the create body is exactly `{ humanName: 'Ana', aiCount: 4, rulesPreset: <defaultPresetId> }`; the slot holds the new `gameId`, the 43-char token, the default preset's deck and `finished: false`; navigation goes to `/game/<gameId>`; the game page shows the empty table, animates the 201 events, and no bid button is rendered until the queue has drained. *(FR-901, FR-902)*
- **VC-902:** presets answers 500 → no create call, no slot, message `No se pudo crear la partida. Probá de nuevo.`, button enabled; create answers 400 → `Revisá los datos de la partida.`, no slot; create rejects (network) → first message, no slot; create never resolves → aborted at 20 s, first message, button enabled. *(FR-903, FR-936)*

## Assumptions

- The default preset's deck can be learned only from `GET /api/presets` at creation (the view has no deck field). Sending `rulesPreset: defaultPresetId` explicitly makes the stored deck match the created game even if `DEFAULT_RULES_PRESET` changes between the two calls.
- One human seat (seat 0) per game, so the UI never has to wait for another human; no polling (spec 07/08).
- Vitest can run `.tsx` component tests in a jsdom environment alongside the existing node-environment tests; the plan chooses the mechanism (per-file environment or a project split) as long as `pnpm test` runs both.
- `crypto.randomUUID` is available in secure contexts of all BR-907 browsers and in the test environment; FR-935 covers non-secure contexts (it is a fallback, not a polyfill).
